Redesigned Competitive Mode Layout (Android
 15)
 Overview: The Competitive Mode chess screen will be modernized with Android 15 (API 35) features,
 while preserving the XML-based View architecture. We will implement a glassmorphic UI motif
translucent frosted-glass panels and floating controls – atop a vibrant backdrop. This involves using
 GPU blur effects, Material 3 theming, and enhanced navigation/transitions. The result will be an
 elegant, immersive interface that takes full advantage of a modern Android 15 flagship’s capabilities.
 Glassmorphic Design with RenderEffect Blur
 Frosted Glass Panels: Key UI containers (e.g. the top player info bar and bottom controls panel) will
 have a frosted glass appearance – translucent with blurred background content. We achieve this by
 layering a semi-transparent shape and applying a GPU blur via
RenderEffect . Android 12+
 introduced
RenderEffect.createBlurEffect() for real-time blurring of Views . In code, after
 inflating the layout, we can do:

 Shader.TileMode.CLAMP)

background

 This will blur the content behind the target view (the panel) when drawing it. Each frosted panel uses a
 custom drawable background – for example, a rounded rectangle shape with a translucent white fill
 (e.g.
#80FFFFFF for ~50% opacity white) and maybe a subtle white outline or inner glow to enhance
 the “glass” illusion. The translucent layer combined with blur produces the acrylic frosted effect .

 Gradient Background: To make the glass effect pop, the app’s root background will be a high-contrast
 gradient or imagery instead of a flat color. A rich, colorful backdrop (for example, a subtle blue-purple
 gradient or a blurred chess-themed image) will show through the translucent panels. According to
 Material and glassmorphism guidelines, a vibrant background accentuates the blur effect . We can

 This gradient might gently vignette toward edges, ensuring foreground text remains legible.
 Furthermore, the blur radius and panel opacity should be tuned together for readability – e.g. using
 ~20px blur radius for depth-of-field and pairing it with a translucent overlay color . Avoid
 excessive blur (Google recommends staying ≤150px radius to prevent performance hits ). Given our
 target is a Galaxy S23-class device, moderate blur (around 20–50px) is feasible without stutter.

 Subtle Shadows/Glows: The frosted panels will also have subtle elevation shadows or glows to stand
 out. We can leverage Material 3 elevation for dynamic shadows – for example, giving the top info bar
 and bottom control panel a small elevation (4dp–8dp) to cast a soft shadow on the background. This not
 only adds depth but also a “halo” glow around translucent edges. Additionally, a faint white stroke on
 panel borders (e.g. 1px with 15% opacity white) can simulate light catching the glass edges. All these
 details contribute to a cohesive glassmorphic aesthetic.

 design fully. Key steps:

android:fitsSystemWindows="true" from layouts

 Predictive Back Navigation
 Android 15 introduces predictive back gesture animations system-wide, providing a visual preview of
 the destination when users swipe back . We will ensure Competitive Mode supports this smoothly:
 15
 •
Enable Predictive Back: As of Android 14+, apps must opt-in to predictive back if they intercept
 back events. In our case, we likely use the default back (to leave the game screen) so minimal
 changes are needed. We will confirm that the manifest (or Activity) hasn’t disabled
 OnBackInvokedCallback. By default, targeting SDK 35 means predictive back is enabled by
 default for the app . We just need to avoid legacy back overrides. In the manifest, we can
 16
 explicitly set
android:enableOnBackInvokedCallback="true" on the application or
 CompetitiveMode activity (though not strictly required if using AndroidX back dispatcher). This
 ensures the system knows our activity is ready for the new back handling.
 4
Using OnBackPressedDispatcher: If the app currently uses
•
onBackPressed() in the Activity
 or a custom KeyEvent handler, we will migrate that to either the AndroidX
 OnBackPressedDispatcher or the platform OnBackInvokedCallback API . This is important
 because intercepting the legacy back event could block the predictive animation. By using the
 modern callbacks, the system can coordinate the gesture with our logic. For example, in
 onCreate() of CompetitiveModeActivity:
17
 onBackPressedDispatcher.addCallback(
 this,
 object : OnBackPressedCallback(true) {
 override fun handleOnBackPressed() {
 // Custom behavior (if any), then:
 remove() // ensure system can proceed with normal back
 onBackPressedDispatcher.onBackPressed() // call default
 }
 }
 )
 If we have no special back behavior (just go to previous screen), we might not need any code at all – the
 default will work with predictive animations out-of-the-box. The main point is not to disable the
 predictive system. (For activities that perform a confirm exit dialog, etc., we’d incorporate that with the
 new APIs so the swipe can be completed if the user confirms.)
 •
18
 Back Animation Preview: With everything enabled, when the user swipes back from the
 Competitive Mode screen, they will see the underlying activity (perhaps a Main Menu or
 Launcher home screen) start to peek in . For cross-task back (back to home launcher),
 Android will show the home screen behind our app during the gesture. For in-app back (e.g.
 from game to a menu activity), the previous Activity’s UI can be previewed. We should ensure
 that previous screen is ready to be drawn. If using multiple activities, consider enabling Cross
activity transitions (described next) so the return transition is smooth in concert with the back
 gesture.
Overall, with predictive back implemented, our app will feel responsive and intuitive on Android 15,
 matching user expectations of the platform navigation.
 Shared Element Transitions
 We will enhance transitions between screens by using shared element animations – for example,
 smoothly transitioning the chessboard view or a piece image between the Competitive Mode and other
 activities (like an analysis screen or a game list). Shared element transitions make the UI feel connected
 and polished. Implementation steps:
 •
Define Shared Elements: Identify which views will be common between activities. A prime
 candidate is the chessboard itself. Suppose when the user taps “Game Analysis” (the FAB), we
 launch GameAnalysisActivity which also displays the final board position. We can make the
 ChessBoardView in Competitive Mode and the one in Analysis share the same transition
 name:
 5
<com.example.ChessBoardView
 android:id="@+id/competitiveChessBoardView"
 android:transitionName="chessboard" … />
 and in analysis layout:
 <com.example.ChessBoardView
 android:id="@+id/analysisBoardView"
 android:transitionName="chessboard" … />
 This tags them for sharing.
 •
•
•
Enable Content Transitions: In the styles or manifest, enable window content transitions for
 these activities. For instance, set the activity theme to include:
 <item name="android:windowContentTransitions">true</item>
 (Material3 themes often have this on by default.) Also ensure
android:windowAllowSharedElementsTransition is true (usually covered by the above).
 We typically also disable the shared elements overlay for a continuous effect:
 getWindow().setSharedElementsUseOverlay(false);
 (This prevents the shared view from duplicating during transition.)
 Launch with Transition: When starting the new Activity, use the AndroidX Activity options to
 specify the shared element. For example:
 val options = ActivityOptionsCompat.makeSceneTransitionAnimation(
 this@CompetitiveModeActivity,
 competitiveChessBoardView,
 "chessboard" // transitionName
 )
 startActivity(intent, options.toBundle())
 This hands off the shared element to the system for animation. We can also include multiple
 elements (e.g. a player avatar or a trophy icon) by pairing them in the options.
 Use Material Container Transform (optional): Given we are using Material Components, we
 can leverage MaterialContainerTransform for a more elaborate shared transition. This is a
 Material motion pattern that morphs a container between activities. For example, if we had a
 card list of games that expands into the game screen, a container transform would animate size
 and shape changes smoothly. To use it, we would set the shared element callback in each
 activity:
 6
// In CompetitiveModeActivity (exit)
 window.sharedElementExitTransition = MaterialContainerTransform().apply
 { ... }
 setEnterSharedElementCallback(MaterialContainerTransformSharedElementCallback())
 // In GameAnalysisActivity (enter)
 window.sharedElementEnterTransition =
 MaterialContainerTransform().apply { ... }
 setEnterSharedElementCallback(MaterialContainerTransformSharedElementCallback())
 Material’s callbacks handle shape rounding and elevation matching during the transition .
 This would give a smooth morphing effect of the board “growing” into the analysis screen, for
 instance. We can tune the transform (duration, interpolator) to match the aesthetic (fast and
 ease-out for a snappy feel).
19
 20
 By implementing shared element transitions, we add a layer of polish: navigating between the
 Competitive Mode and other parts of the app will feel fluid, as elements don’t abruptly disappear but
 gracefully transform. This is especially effective on a high-performance device where complex
 transitions run at 60+ FPS.
